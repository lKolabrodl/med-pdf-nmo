# Improvement Theories

Документ описывает следующий раунд гипотез по улучшению `med-pdf-nmo` и их
**корреляцию с уже пройденными 155 итерациями**. Цель — не запускать заново
направления, которые журнал уже опроверг, а сосредоточиться на действительно
открытом и структурно-обоснованном пространстве.

Как читать: сначала — управляющее ограничение (потолок из итерации 84) и
чёрный список закрытых направлений. Затем каждая теория дана с полем
«корреляция с итерациями»: какие прошлые попытки её касаются, чем новая
формулировка от них отличается и какой у неё честный потолок. Теории, чей
наивный вариант уже опровергнут, помечены и сознательно сужены.

Метрический ориентир (на момент написания): all keyed ≈ `74.8–75.5%`,
single `82.6%`, multi exact-set `58.2%`, замороженный holdout `≥0.85`,
внешний transfer `86.0%`.

## Результат практической проверки, итерации 156–163

Все семь теорий ниже теперь проверены. В раунд также заранее добавлен новый
сложный внешний PDF `51-travma`; поэтому размер корпуса вырос до `2,867` keyed
вопросов, а прежние `86.0%` external больше нельзя сравнивать напрямую с новым
external из `263` вопросов.

| Теория | Практический результат | Решение |
| --- | --- | --- |
| T1, единая table-grid модель | 140 новых безопасных строк на dev, но `0` изменённых ответов; `416/523` | runtime-реализация удалена |
| T2, структурная кардинальность | затронуты 4 уже правильных dev-вопроса; `0` изменённых наборов | runtime-реализация удалена |
| T3, когерентное подмножество | те же 4 уже правильных вопроса; отдельно и вместе с T2 — `0` delta | runtime-реализация удалена |
| T4, отрицание/исключение | исправленный negation detector дал `0` delta; строгий exclusion resolver не нашёл ни одного применимого случая | runtime-реализация удалена |
| T5, ремонт split-token | структурно ограниченная версия исправила `15-toxic#54`, не сломав остальные сплиты | **принято** |
| T6, PDF-group stability/LOO | добавлен честно названный fit-free per-PDF audit; нового sealed набора в репозитории нет | tooling принято |
| T7, ablation | 19 активных флагов проверены; единственный apparent `+1` на `51-travma` дал `−1` на dev | runtime без изменений |

Итог default-конфигурации после принятого T5:

- train `1074/1541 = 0.6970`;
- dev `416/523 = 0.7954` (`+1`);
- holdout `460/540 = 0.8519` (без изменений);
- external `175/263 = 0.6654` (без изменений);
- all keyed `2125/2867 = 0.7412`, было `2124/2867 = 0.7408`.

Следовательно, теории были реальными и реализуемыми, но оценки headroom у
T1–T4 оказались слишком оптимистичными: безопасные гейты почти всегда
срабатывают на уже решённых вопросах. Из accuracy-гипотез измеримый общий
прирост дала только T5. Подробные артефакты и причины отклонения записаны в
`docs/iteration-log.md`, итерации 156–163.

После финального решения в итерации 165 из runtime оставлен только T5. Описания
флагов и контрактов ниже сохранены как исходный план экспериментов, а не как
действующие возможности production predictor.

## 0. Управляющее ограничение: что уже доказано о потолке

Два факта из `error-analysis.md` и журнала задают рамку для всего документа.

**Retrieval — не проблема.** `noEvidence = 0` на всех сплитах. Нужный текст
находится почти всегда; баллы теряются на *владении* (ownership): какая строка
таблицы, какой пункт списка, какой target рекомендации, какое множество ответов.
Отсюда правило: любой рычаг, повышающий вес поиска (BM25, ширину окна, shared-chunk),
усиливает дистракторы и уже отклонялся. Улучшение — это ремонт представления и
доказательство отношения в ограниченном фрагменте, а не рост охвата.

**Итерация 84 количественно замерила multi-рычаг и нашла потолок.** Разбор
385 multi-ошибок: списки-членство (`«К группе/классу X относятся …»`) — `105`,
списки-рекомендации — `59`, прочее — `204`, чисто координатные таблицы — `~17`.
Ключевой вывод, который управляет теориями ниже:

> **Членство в списке ≠ правильность.** Уплощённый (flattened) список часто
> содержит и правильные пункты, и дистракторы с *идентичным* структурным
> членством. Любой выбор по членству меняет исправление недобора на поломку
> перебора (нетто ≈ 0). Различить их нельзя без семантики, которую уплощённый
> текст не сохраняет.

Конкретно в итерации 84 вариант V3 («выбрать ровно членов чистого структурного
list-сегмента», то есть связать И членство, И кардинальность) дал dev `+1`, но
holdout `−1` (`14-sarkoidoz#38`: дистрактор, который тоже является членом
списка). Реванш через подстройку порога под holdout-кейс был признан
переобучением.

Практическое следствие для этого раунда: **координатные таблицы и flat-списки —
разные вещи**. Таблицы дают ограниченный, но реальный слайс (ownership строк/
столбцов). Flat-списки-членство — почти закрытый потолок для non-LLM. Поэтому
теории 1/2/3 ниже сознательно ограничены *контрастной* структурой (sub-метки,
строки/столбцы с раздельным владением, parent-child), где сигнал ещё есть, и не
претендуют на flat-membership слой.

### T1. Единая модель таблицы/блока на уровне экстракции

**Цель / класс ошибок.** «table/layout ownership» — `47` single; «table without
layout evidence» — `23` multi; «parsed table still ambiguous» — `14` multi
(координаты есть, но merged cells и повторные заголовки не разрешаются). Верхняя
граница по multi из итерации 84 — `~17`. Итого реалистичный слайс ≈ `60–75`
кейсов. Это не «главный рычаг», но самый структурно-обоснованный и переносимый.

**Корреляция с итерациями.**

- Уже сделано как *набор узких scorer'ов*: `visual_table_column` (40),
  `coordinate_table_row` (42), bounded relational rows (128), header
  propagation и table-region bounds (134–136), рефакторинг в `coordinate-table/`
  (152–153).
- Отклонено: широкие координатные строки без гейтов (127), использование
  координатных строк для multi и recommendation-meta строк (42).
- **Чем T1 отличается.** Сейчас шесть scorer'ов *каждый сам* кластеризует items
  под свой паттерн вопроса. Единого представления «сетка ячеек страницы» нет.
  T1 не добавляет новый *scoring*-сигнал (это и проваливалось в 127/42), а
  поднимает реконструкцию на уровень экстрактора как **представление** — рядом
  с уже существующими `page.lines` и `page.blocks`. Потребление остаётся за теми
  же гейтами, что и сейчас. Провал 127 был в том, что *слабую* сетку сразу
  пускали в счёт очков; здесь сетка сначала строится и оценивается по
  уверенности, и только надёжная сетка доступна scorer'ам.

**Реализация.**

1. Новый модуль `src/predictor/table/grid-builder.ts` (или `coordinate-table/grid.ts`),
   вызывается один раз на страницу в `context-builder.ts`. Вход — `lineItems`
   (x/y/ширина из `pdf.ts`). Алгоритм в духе Camelot Stream (уже упомянут в
   research.md):
   - строки: кластеризация items по перекрытию y;
   - столбцы: границы по устойчивым x-разрывам (whitespace gaps) на нескольких
     строках;
   - ячейки: `{ row, col, text, bbox }`;
   - **новое сверх текущих scorer'ов**: детекция merged cells (ячейка,
     покрывающая ≥2 колоночных диапазона), повторных заголовков (одинаковая
     верхняя строка на нескольких страницах), продолженных строк через разрыв
     страницы.
2. Тип `TableGrid` в `coordinate-table/types.ts`; кэш `page -> TableGrid[]`
   в `PredictionContext` (по образцу текущего координатного кэша).
3. Каждой сетке — поле `confidence` и флаг `lowConfidence` (мало строк,
   прозаический регион, нестабильные колонки, аномально длинные строки —
   вероятное слияние колонок). Scorer'ы **обязаны abstain** при `lowConfidence`.
4. Существующие `coordinate_table_row/_group/_multicell_row/_membership` и
   `visual_table_column` переписываются на чтение общей сетки вместо собственной
   кластеризации. Регистрация evidence-kinds — без изменений, через
   `scorer-registry.ts`.

**Гейты abstention.** Подпись «Таблица …» рядом или ≥2 правдоподобных строки;
ответ и фокус в *разных* ячейках; покрытие ответа; контраст строк-соседей
(iter 128). Для merged/continued — заголовок должен быть однозначно определён до
применения границы региона (iter 136). Никаких медицинских фактов/имён PDF.

**Тесты.** Синтетические сетки: (а) merged cell на 2 колонки; (б) продолженный
заголовок через разрыв страницы; (в) отклонение прозаического региона как
`lowConfidence`; (г) zero-delta на всех четырёх сплитах для кейсов, которые уже
проходили старыми scorer'ами (регрессионный контракт как в 152–153).

**Риск.** Средний. Основной — ложные сетки на flat-колонках; смягчается
`lowConfidence` + обязательным abstention. Обязателен полный diff по 4 сплитам
(`scripts/diff-results.mjs`).

**Потолок.** `~60–75` кейсов, из них multi `~17`. Не решает flat-membership
(раздел 0) — это надо явно зафиксировать в PR.

### T2. Кардинальность из *контрастной* структуры (сильно ограниченная форма)

**Цель / класс ошибок.** Multi-кардинальность: недобор `141`, перебор `104`,
«верное число — неверный член» `107`. Оракул с истинным K: multi dev
`0.686→0.788`, holdout `0.727→0.825` — потенциально крупнейший рычаг.

**Корреляция с итерациями — читать внимательно.**

- Наивная форма **уже закрыта**: обученная модель кардинальности по форме score
  (106, 51) и «выбрать членов чистого list-сегмента» (84 V3) дали нетто-нуль/
  регресс. Скалярные пороги (8, 44, 45) — тоже.
- Что *работало*: `sibling_list_multi_segment` (110) — потому что различает
  членов под *целевой* меткой и под *соседними* метками; hierarchical
  parent-child (120); explicit ordinal range/list decoder (99). Все три
  используют **внутреннюю контрастную субструктуру блока**, а не плоское
  членство.
- **Чем T2 отличается.** T2 берёт K не из формы score и не из плоского членства,
  а только из блока, у которого есть контрастная субструктура: считает, сколько
  опций отображаются на *различимые* элементы (sub-метки sibling-кластера, строки
  таблицы с раздельным владением из T1, дети одного parent). Если различимости
  нет — блок плоский — T2 **не срабатывает вообще** (это и есть урок 84).

**Реализация.**

1. Новый пост-процессор `structuralCardinality` в
   `src/predictor/pipelines/score-adjustment-processors.ts`, включаемый флагом
   `config.structuralCardinality` (по умолчанию off до валидации).
2. Работает *после* существующих sibling/hierarchical/table резолверов и читает
   их провенанс: если ≥2 выбранных кандидата привязаны к *различным* элементам
   одного контрастного блока, K_struct = число различимых элементов блока,
   совпавших с фокусом.
3. Использует K_struct только чтобы (а) допустить до K_struct кандидатов в
   raw-порядке, которые *также* имеют членство в этом блоке; (б) не трогать выбор,
   если блок не разрешён однозначно.
4. Никогда не превышает число опций; не отменяет hard-правило min-2; не читает
   ожидаемое число ответов.

**Гейты abstention.** Блок должен быть однозначно сопоставлен вопросу; элементы —
различимы (есть sub-метки/строки/дети, а не один абзац); при конкуренции двух
блоков — abstain; при `lowConfidence`-сетке из T1 — abstain.

**Тесты.** (а) sibling-кластер с 3 целевыми под одной меткой + дистрактор под
соседней → K корректен; (б) плоский список без sub-меток → процессор не
срабатывает (контрактный тест на «no-op»); (в) конфликт двух блоков → abstain;
(г) регрессия: множество кейсов 110/120/99 не должно измениться.

**Риск.** Высокий по репутации (соседний вариант проваливался). Обязателен
LOO-CV (T6), а не только dev/holdout. Если на LOO нетто ≤ 0 — отклонить и
задокументировать как ещё один вариант 84.

**Потолок.** Скромный и только на контрастных блоках. Явно НЕ покрывает `105`
flat-membership ошибок.

### T3. Выбор когерентного подмножества (обобщение shared-segment)

**Цель / класс ошибок.** Перебор `48` («сосед из общего абзаца влез в набор») и
«верное число — неверный член» `107`.

**Корреляция с итерациями.**

- `sharedSegmentBoost` (34) уже поднимает кандидата, указывающего на тот же
  качественный сегмент. Generic structural-cluster pruning (43) добавлен, но
  *отгорожен* от broad-list/source/dose паттернов, потому что более широкий
  вариант регрессировал.
- **Чем T3 отличается.** Не менять веса/пороги (это класс закрытых направлений),
  а сделать провенанс-осведомлённый выбор: предпочесть подмножество, чьи члены
  привязаны к *одному* контрастному блоку, и штрафовать член, чьё единственное
  подтверждение — другой блок/общий абзац. Это ужесточение уже существующей
  логики 34/43, а не новый broad-сигнал.

**Реализация.**

1. Расширить контракт evidence в `scorer-registry.ts`: структурные scorer'ы
   тегируют лучшее evidence `blockId` (идентификатор восстановленного блока/строки/
   bullet).
2. Пост-процессор `subsetCoherence` в `score-adjustment-processors.ts`: кластеризует
   выбранных+кандидатов по `blockId`; при наличии доминирующего блока предпочитает
   подмножество из него; член только-из-другого-блока получает мягкий штраф.
3. Строго: срабатывает только при доминирующем блоке; при ничьей — abstain; не
   отменяет сильное независимое структурное evidence.

**Гейты / тесты / риск.** Аналогично T2: no-op на плоских случаях, регрессионный
контракт на 34/43, LOO-обязателен. Риск средний; ловушка — перебор, поэтому
дефолт off и жёсткие гейты.

**Потолок.** Пересекается с T2; вместе бьют по перебору/неверному члену на
контрастных блоках. Оценивать их следует *совместно* на LOO, а не по отдельности
на dev.

### T4. Отрицание/исключение на уровне вопроса (инверсия членства)

**Цель / класс ошибок.** `negative/exception scope` — `28` single + часть multi:
«кроме», «за исключением», «не рекомендовано», «не характерно», исключение
подгруппы переворачивают сильное лексическое evidence.

**Корреляция с итерациями.**

- Отклонено: exact-negation-pair (114) — но это про *парные опции одного
  скелета*, которых в корпусе почти нет.
- Работает узко: `mkb_class_exclusion_absent` (49) — инверсия членства для
  `«по МКБ-10 в класс Cxx не включены»`.
- **Чем T4 отличается.** T4 — обобщение 49, а не 114: детектор отрицания в
  *стебле вопроса* инвертирует решение о членстве внутри *уже восстановленного*
  списка/класса (из sibling/hierarchical/T1), а не сравнивает пары опций.

**Реализация.**

1. Детектор negation-cue в вопросе (`кроме`, `за исключением`, `не относят`,
   `не включ`, `не рекомендов`, `не характер`, `не типич`, `не показан`) с
   границами по кириллице (не JS `\b`, как уже принято в проекте).
2. Новый scorer `src/predictor/scorers/exclusion/index.ts` (или расширение
   `direction/`): при negation-cue И однозначно восстановленном списке-кандидате —
   выбрать опции, которых в списке *нет* (или штрафовать те, что есть).
3. Разбиение противительных клауз; abstain если в блоке присутствуют обе
   полярности.

**Гейты.** Требуется восстановленный список (sibling/hierarchical/table), а не
широкий абзац; иначе abstain. Никаких медицинских фактов.

**Тесты.** (а) `«… кроме»` + класс с явными членами → инверсия; (б) неоднозначная
полярность → abstain; (в) отсутствие восстановленного списка → no-op.

**Риск.** Низкий–средний. Класс небольшой, но ошибки токсичны; поэтому
консервативные гейты важнее охвата.

**Потолок.** `~28` single + небольшой multi-хвост.

### T5. Документ-внутренний ремонт разорванных токенов

**Цель / класс ошибок.** Локальные искажения токенов, питающие ошибки OCR-fuzzy и
numeric-family. Аудит: `1 831` строка с переносом-дефисом; внутрисловные разрывы
вида `Гры жа`.

**Корреляция с итерациями.**

- Отклонено: широкая кириллическая OCR-похожесть (129); оставлен только
  bounded `ocr-fuzzy` (130).
- Прямо *предложено, но не сделано* (`error-analysis.md`, cleanup): «consider a
  conservative document-internal lexicon for intra-item splits such as `Гры жа`,
  but do not globally concatenate short words».
- **Чем T5 отличается.** Не похожесть/edit-distance (класс 129), а склейка по
  доказательству из *самого документа*: разрыв соединяется только если склеенный
  токен встречается в этом PDF как цельное слово.

**Реализация.**

1. На этапе экстракции (`pdf.ts`/`normalize.ts`) построить пер-PDF лексикон
   цельных токенов с частотами.
2. При обычном переносе-дефисе (уже частично есть) и при пробельном
   внутрисловном разрыве — склеивать, только если склеенная форма есть в лексиконе
   с частотой ≥ порога, и ни один фрагмент не является валидным самостоятельным
   словом/числом.
3. Без глобальной конкатенации коротких слов.

**Тесты.** (а) `Гры жа`→`Грыжа` при наличии `Грыжа` в документе; (б) реальная
пара из двух слов не склеивается; (в) число не приклеивается к слову.

**Риск.** Низкий: доказательство берётся из документа, охват узкий. Тем не менее —
полный diff по 4 сплитам, т.к. меняется текст на входе всех scorer'ов.

**Потолок.** Небольшой, но чистит вход для нескольких семейств сразу.

### T6. Запечатанный тест + leave-one-PDF-out (измерение, а не accuracy)

**Цель.** Восстановить доверие ко *всем* цифрам. Это предпосылка для T1–T3:
без честной оценки обобщения «+N на dev» может не переноситься — ровно
повторяющийся паттерн провалов в журнале.

**Корреляция с итерациями.**

- `research.md`/`error-analysis.md` сами фиксируют: holdout **информировал 100+
  итераций** и является regression/acceptance-набором, а не слепой оценкой;
  рекомендация №4 — «obtain a genuinely new, label-sealed PDF test set».
- Итерация 84 сделала вывод о потолке non-LLM архитектуры — тем важнее иметь
  чистую метрику, чтобы понимать, стабильны ли текущие `74.8%` вообще.
- Репродьюсибилити-оговорка: в git отслеживаются только `5` из `46` case-файлов;
  метрики держатся на локальном датасете.

**Реализация.**

1. `scripts/eval-loo.ts`: leave-one-PDF-out по группам — каждая PDF-группа по
   очереди held-out, агрегат по всем. Это становится основным сигналом
   обобщения вместо фиксированного dev/holdout.
2. Протокол запечатанного набора: каталог новых PDF, чьи `cases.test.ts`
   **никогда не открываются** при разработке; валидатор хэширует метки и не
   показывает их; наружу — только финальный агрегат.
3. Решить вопрос воспроизводимости: либо трекать все `46` case-файлов в git,
   либо явно задокументировать зависимость метрик от локального датасета и его
   fingerprint.

**Риск.** Отсутствует для рантайма (изменений в скоринге нет). Стоимость —
время прогонов (LOO дороже одиночного eval).

**Ценность.** Наивысшая среди всех теорий: превращает остальные из «плюс на
загрязнённом dev» в проверяемые.

### T7. Аудит вклада scorer'ов (упрощение + возможный выигрыш)

**Цель.** `~50` scorer'ов за 155 итераций; часть могла стать нетто-нулевой или
отрицательной после поздних правок.

**Корреляция с итерациями.**

- Прецеденты: удаление мёртвого `condition_number_segment` (154), отключение
  `negation-pair` (114). T7 систематизирует это.

**Реализация.**

1. `scripts/ablation.ts`: по очереди отключать каждый scorer/evidence-kind через
   config-флаг, прогонять все сплиты (в идеале LOO из T6), фиксировать дельту.
2. Где флага нет — добавить toggle (частично уже есть: `frozenFeatureRanker`,
   `negationPairClauseResolver`, `multiCardinalityModel` и т.д.).
3. Ранжировать по нетто-вкладу; нетто-≤0 — в карантин/удаление.

**Риск.** Низкий; результат — снижение сложности и, возможно, малый прирост за
счёт удаления шумных сигналов.

## 3. Приоритет и последовательность внедрения

Сначала — дешёвое и измерительное, затем — структурное, последними — рискованные
кардинальностные (после того как появится честная метрика).

1. **T6** (LOO-CV + запечатанный набор) — первым: без него остальные не
   проверяемы.
2. **T7** (ablation) — дёшево, чистит поле и даёт baseline вкладов.
3. **T5** (token repair) — низкий риск, эндорснут доками, не сделан.
4. **T1** (единая модель таблицы) — основной структурный лоскут (`~60–75` кейсов),
   в безопасном паттерне ремонта представления.
5. **T4** (отрицание вопроса) — узкий, токсичный класс, распараллеливается с T1.
6. **T2 + T3** (кардинальность/когерентность на контрастной структуре) —
   последними и **только на LOO**, оценивать совместно. Наивные варианты закрыты
   (84 V3, 106); допустима только сильно ограниченная форма, иначе — задокументировать
   как повторный отрицательный результат.

Общий тезис: реалистично адресуемый безопасный слайс — таблицы (T1), отрицание
(T4), чистка токенов (T5) и упрощение (T7), плюс, возможно, узкая контрастная
кардинальность (T2/T3). Слой flat-membership (`~105` multi) итерация 84 признала
непокрываемым текущей non-LLM архитектурой; T6 нужен, чтобы честно измерить, где
на самом деле проходит текущая граница.

## Приложение A. Расхождение цифр в доках

`README.ru.md` считает по `2 684` keyed (`45` групп, all keyed `74.78%`),
`error-analysis.md` — по `2 754` keyed (`46` групп, `75.45%`). Это разные снимки
корпуса (до/после добавления `50-dr-gepatit`). Рекомендуется синхронизировать
метрики в доках и явно указывать fingerprint манифеста рядом с цифрами, чтобы
таблицы не расходились между файлами.

## Приложение B. Инварианты, которые нельзя нарушать

- Non-LLM: рантайм под `src/` не импортирует eval/answer-key/split-файлы,
  сетевые клиенты, LLM/transformer/embedding-сервисы (leakage-тесты в `npm test`).
- В рантайм-правила не попадает: id кейса, имя PDF/группы, номер страницы, текст
  ответа, ожидаемое число ответов, медицинский факт.
- Каждое изменение — с полным diff по train/dev/holdout/external
  (`scripts/diff-results.mjs`) и, для скоринговых изменений, с LOO-проверкой (T6).
- Дефолт для нового scorer'а — off + focused-тесты, включение только после
  агрегатной валидации без регрессии holdout (гейт `≥0.80`).
